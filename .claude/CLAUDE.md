# OBS Scoreboard

Live football broadcast graphics. Two static React pages (Vite multi-page build, plus the output's static thumbnail page) synced through Firestore:

- **Output** (`src/overlay/`): the on-air page with every scene (scoreboard, welcome, player intro, goal scorer, player card, lineup, half/full time, sponsors). It's shown full screen in a browser on a projector or second monitor, opened from the control page; no broadcast software (OBS, vMix, …) is involved. Read-only, no login.
- **Control** (`src/control/`): the operator dashboard, with a grouped sidebar menu and five pages: **Match setup** (`#/match`: match teams, away players switch, lineup, kick-off check, resets; changes show on air at once), **Live** (`#/live`, the default: scenes, score and goals, clock and halves, player intro, lineup edits in a dialog), **Teams** (`#/teams`: searchable, filterable table of clubs; a row opens a drawer with the details and the squad with PNG photos; the old `#/setup` opens it), **Sponsors** (`#/sponsors`: the account's own sponsor list, see **Sponsors**) and **Graphics** (`#/graphics`: global theme and colour scheme, scene options). Requires Firebase Auth login.

There is no backend. The pages talk directly to Firebase. Production is GitHub Pages + project `granicar-scoreboard`. See **Environments** for local and staging, and README.md for one-time setup.

## Data store and offline

The UI never imports Firebase. All reads and writes go through the `DataStore` interface (`src/shared/store/types.ts`: `auth`, `match`, `teams`, `players`, `sponsors`, `scenes`, `graphics`, `graphicsDraft`, `sync`), picked by `createStore()` (`src/shared/store/index.ts`) and provided to React with `StoreProvider` / `useStore()` (`src/shared/react/store.tsx`). Today the only implementation is `src/shared/firestore/` (Firebase config, workspace paths, one `*Repo.ts` per API).

Offline is a planned feature, in two stages:
- **Network drops (works now):** Firestore uses a persistent multi-tab IndexedDB cache. Pages load the last state without a connection, writes are applied locally at once and sync on reconnect, and Auth keeps the session. The dashboard shows "Offline" (from `store.sync`, bottom right) after 3 s disconnected.
- **Fully local at the venue (planned):** a `local` `DataStore` (control and output page on one machine syncing through a local hub) chosen in `createStore()`. No UI changes should be needed.

Rules that keep both working: keep store operations domain-level ("record a goal"), not path-level. **No Firestore transactions or server reads in write paths**, because they fail offline (`recordGoal` uses `increment` / `arrayUnion`, `removeLastGoal` works from the caller's snapshot). **Never block the UI on a write promise.** Offline it only settles on reconnect, so fire with `void`. `create()` returns the new id synchronously for the same reason.

## Data model

Everything lives under `workspaces/{WORKSPACE_ID}` (`src/shared/firestore/workspace.ts`, single tenant `"default"` for now; multi-tenancy means choosing this id per customer). Types are in `src/shared/types.ts`.

| Path | Type | Firestore repo (`src/shared/firestore/`) |
|---|---|---|
| `live/match` | `MatchState`: `score`, `clock`, `teams` (side → team id), `lineup` (side → ordered player ids), `awayPlayers`, `goals[]`, `program`, `half` | `matchRepo.ts` |
| `teams/{id}` | `TeamProfile`: name, shortName, city, colours, `logo`, `playerCount` / `missingPhotos` (denormalized squad counts, null on older teams), `updatedAtMs` (null on older teams) | `teamRepo.ts` |
| `players/{id}` | `Player`: `teamId`, full `name`, `photo` (PNG cut-out) | `playerRepo.ts` |
| `sponsors/{id}` | `Sponsor`: `name`, `logo` (PNG), `tier` (`main` / `partner`), `order`, `hidden` (left out of the scene) | `sponsorRepo.ts` |
| `scenes/{sceneType}` | `SceneConfig`: title, subtitle, `background`, `logo` (scoreboard: competition logo), `layout`, `secondsPerSponsor` (sponsors only) (accentColor unused) | `sceneRepo.ts` |
| `settings/graphics` | `GraphicsSettings`: global `theme` id + colour scheme `colors` + scene `transition` id | `graphicsRepo.ts` |
| `drafts/graphics`, `drafts/scene-{type}` | Graphics draft: `GraphicsPatch` / `ScenePatch`, only fields that differ from on air (no doc = no change) | `graphicsDraftRepo.ts` |

`firestore.rules`: anyone can read `workspaces/**`, and only signed-in users can write. The old `matches/current` doc is no longer used. Its rule is kept so older deployed overlays still load.

**`subscribeToLive(store, …)` (`src/shared/liveFeed.ts`)** is what both pages use, once per page via `LiveDataProvider` (read with `useLiveData()`). It subscribes to the match, then only to the two selected teams and their players (re-subscribing when the teams change), plus the scene configs, all of the workspace's sponsors and the graphics (theme + colours). It emits a combined `LiveData` (`match`, `teams`, `players` map, `squads` and ordered `lineups` per side, `scenes`, `sponsors`, `graphics`).

**Lineup and the home-team focus.** Before the game the operator ticks who is playing and orders them (Match setup > Lineup, or Live > Edit lineup; both use `LineupEditor`); `match.lineup[side]` holds the ordered ids, and pure helpers live in `src/shared/lineup.ts` (tested). **Every scene and picker uses `matchPlayers(data, side)`**: the lineup once one is picked, else the whole squad. `match.awayPlayers` (off by default) says whether the away squad/photos exist; when off, `sidesWithPlayers()` is home-only: away players aren't loaded, away goals skip the scorer picker, and "Lineup away" is hidden. Changing a side's team clears its lineup; full reset keeps teams and lineups. The Teams page subscribes to the full team list (via `TeamsProvider`), and to a team's players while its drawer is open (Squad tab and Remove team take them from that one subscription, so deleting a team needs no server read).

**Team squad counts** (`playerCount`, `missingPhotos`) are denormalized for the team cards and kept by the players store operations in the same batch, with `increment` (offline-safe): `players.create(fields)`, `players.update(current: Player, fields)` (photo set/cleared, team moved) and `players.remove(player: Player)` take the caller's snapshot of the player; the deltas come from the pure `playerStatDeltas(before, after)`. The team bump is a separate write from the player's (a missing team must not fail the player, and a merge write would resurrect a deleted team); a failed bump is only logged. They are null on teams saved before them (and an `increment` starts a null count from the delta), so whenever a team's whole squad is loaded (the drawer's Squad tab, and only while `store.sync` is connected with no pending writes) the Teams page compares with `staleTeamStats(team, players)` (`src/shared/squad.ts`, tested) and repairs with `teams.setStats(id, stats)` (a failed repair, e.g. a team deleted meanwhile, is only logged, never a save-error warning). `teams.create` / `update` stamp `updatedAtMs` (`compareRecentlyEdited` sorts by it). `teams.remove(id, playerIds?)` deletes from the caller's squad ids when given (offline-safe), else it still reads the players from the server. Bulk writes go through `commitInChunks()` (`firestore/batch.ts`, ≤450 ops per batch); every partial update strips undefined with `withoutUndefined()` (`src/shared/objects.ts`), since Firestore rejects it. Team, player and sponsor edits still show on air at once.

**Graphics draft** (`drafts/`, `src/shared/graphicsDraft.ts` pure helpers, tested). What the Graphics page changed but hasn't put on air, shared by every control page: one `GraphicsPatch` (theme / whole `colors` / transition) and one `ScenePatch` per scene, each holding only fields that differ from on air (`OnAirGraphics` = saved `graphics` + `scenes`). The page shows `applyDraft(onAir, draft, edit)`, saves `store.graphicsDraft.save(diffDraft(onAir, shown), stored)` (writes only the docs whose patch changed, an empty patch deletes its doc; one batch), and goes on air with `store.graphicsDraft.publish(draftChanges(onAir, draft))` (one batch: each patch's fields replace the on-air doc's with `mergeFields`, so `colors` is never deep-merged; a null image clears it; all draft docs deleted) or drops it with `discard()`. `draftChanges()` ignores stale fields (on air changed under the draft); `summarizeDraft()` names what changed. Drafts are publicly readable like the rest of `workspaces/**` (no rules change). `scenes` and `graphics` are read-only in the store: `publish()` is the only way the look and scene configs change on air.

**Images are inline data URLs.** There is no Cloud Storage, because it needs the paid Blaze plan. `fileToResizedDataUrl` (`src/shared/image.ts`) resizes client-side. Image kinds are in `src/control/images.ts`: logos are PNG at 600px, player photos are PNG at 800px (transparent cut-outs), scene backgrounds are JPEG at 1920px. `processImage()` scales an image down further until its data URL fits (`MAX_DATA_URL_LENGTH`). "Add players from photos" creates one player per file, named by `nameFromFileName()`. Each image sits on its own team/player/scene doc so every doc stays under Firestore's 1 MiB limit. Don't put images on the match doc. React only touches an `<img src>` when the data URL changes, so large images aren't re-decoded per snapshot.

**Schema evolution.** The backend-neutral normalizers in `src/shared/normalize.ts` merge loaded data over defaults, so docs written by older versions still render. When you add a field: add its default in `types.ts` (`createInitialMatchState()`, `NEW_TEAM`, `DEFAULT_SCENE_CONFIGS`, …), handle it in `normalize.ts`, and write match fields with dotted paths (`updateDoc(ref, { "teams.home": id })`). `match.reset()` overwrites the match doc with `setDoc` (keeping the selected teams), which also removes stale fields.

## Clock and program: state, not counters

**Clock.** `ClockState` = `{ running, startEpochMs, accumulatedMs }`. Every client derives elapsed time locally (`computeElapsedMs`) and re-renders on a 250 ms `setInterval`. Firestore is written only on start/pause/adjust, so reloads and network blips cause no drift.

**Program (what's on air).** `ProgramState` = `{ scene, side, playerId, startedAtMs }`. **Nothing changes scenes automatically:** a scene stays on air until the operator takes another one (no timers or auto-return; the old `autoReturnMs` / `durationMs` fields may linger on stored docs and are ignored). "Take" = `store.match.setProgram(takeScene(scene, Date.now(), target))`. `removeLastGoal()` undoes a goal.

**Goal flow**, every step manual: only the Scenes panel changes what's on air, the Score panel only edits data. 1) **GOAL!** (Scenes panel) takes the goal scene, which is generic: title, both crests and the live score (on the Classic theme instead "GOOOOOL" scrolling in screen-high letters, the welcome `Marquee` with the goal scene's subtitle). 2) Behind it, **+** (Score panel) = `recordGoal()` (bumps the score, appends a `GoalEvent` with no scorer and the match time computed by the caller), so the score changes on air, and opens the "Who scored?" popover (search, players, Unknown scorer, Later); picking = `setGoalScorer()` (`withLastScorer()` in `src/shared/goals.ts`, from the caller's snapshot), now or later via Set/Change scorer. 3) The Scenes panel's player card selector jumps to the latest goal's scorer: Take. 4) **Scoreboard**.

**Player intro** (`presentation` scene) is taken from the Scenes panel ("Player intro", "Player intro away" with away players) and opens on the club's crest (no `playerId`). The Player intro panel (always shown, enabled only while the intro is on air) has Prev/Next (`stepIntro()`: logo → player 1 … → last, Prev from the first back to the logo), also on arrow keys or PageUp/PageDown (presenter clickers) on the Live page (not while a dialog or popover is open on the shown page), timed to the commentary; it shows one lineup player at a time and stays on air. `PresentationPanel.tsx` remembers its last take until the snapshot catches up, so fast double presses advance twice. **The player card uses the same design** (`PlayerIntro` in `scenes.tsx` renders both scenes), for the player taken from the Scenes panel.

**Sponsors.** The account's own sponsors (the workspace is the account; never a team's sponsors), managed on the Sponsors page (`src/control/sponsors/`: every sponsor comes from a logo file, one or many at once, with a list-only name from `nameFromFileName()`; two sections, Main and Partners, as a grid of tiles or a compact list (choice kept per browser in `localStorage`); drag a tile within a section to reorder or onto the other one to change tier (`placeSponsor()` / `stepSponsor()` in `sponsors/sponsorOrder.ts`, tested, then `store.sponsors.reorder(ids, current)` with the full list, or `store.sponsors.place(id, tier, ids, current)` for a move into the other tier (tier + order together); one batch, writing only the sponsors whose `order`/`tier` differ from `current` (`sponsorOrderWrites()` in `src/shared/sponsors.ts`, tested)); each tile's ⋯ menu has every action (move up/down, tier, hide/show on air, replace logo, rename, delete) for the keyboard; tick tiles for the bulk bar (it acts only on visible ticked tiles; a new search or Show hidden setting clears the selection); a red banner warns while the sponsors scene is on air, since edits show at once; dragging is off while searching). **The scene shows images only, never sponsor names**; sponsors without a logo and hidden ones (`hidden`) are left out (`sponsorsByTier()`). Bulk edits: `store.sponsors.updateMany(ids, { tier?, hidden? })` and `removeMany(ids)`, one batch each. The `sponsors` scene is taken from the Scenes panel (no side) and has two layouts: `grid` (default; main sponsors' row over the partners' rows, columns from `gridColumns()`, logos `object-fit: contain` in equal boxes) and `single` (one large logo at a time, main sponsors first; on Classic straight over the background, no card). Which sponsor is up, and its 30 fps fade, come from `sponsorSlide(count, program.startedAtMs, now, secondsPerSponsor)`, so every output window agrees and a reload doesn't restart it; `SponsorRotation` writes the opacity directly (timeout while solid, animation frames only while fading). Pure helpers in `src/shared/sponsors.ts` (tested). Cover transitions keep the home team's logo on the curtain.

**Halves.** `match.half` (1 or 2) labels the scoreboard. The half buttons (Live strip, "Clock ⋯" popover) call `startHalf()` with `halfStartClock()` (stopped at 00:00 / 45:00, in `clock.ts`); End half (`endHalf()`) only pauses the clock; half time / full time are taken from the Scenes panel. Full reset goes back to the 1st half.

**Match writes never fail silently.** All Firestore match updates go through `updateMatch()` (`firestore/matchRepo.ts`), which recreates a missing `live/match` doc and retry. The control page shows a top-bar warning for any rejected Firestore write (`unhandledrejection`), and every `onSnapshot` has an error handler (`logSubscriptionError`), because a failed listener stops for good. Each dashboard panel sits in a `PanelBoundary` and each page in a `PageBoundary` (`App.tsx`), so one crashing panel or page doesn't take the others down; if the Graphics draft provider fails, the pages render without it.

`clock.ts` and `program.ts` are pure functions taking `nowMs`. Keep them pure, pass `Date.now()` from the caller, and add tests in `clock.test.ts` / `program.test.ts`.

## Control page structure

`src/control/App.tsx` shows the login until Auth reports a user, then the dashboard: the sidebar (brand, env badge, nav grouped as Match day: Match setup, Live / Library: Teams, Sponsors / Design: Graphics, the Output box (status dot + "Not open" / "Open on <screen>, not fullscreen" / "Fullscreen", output URL with copy/open (with several screens in Chrome/Edge, Open lists them via the Window Management API and opens a window covering the chosen one; otherwise a new tab; once that window reports in, a Fullscreen button puts it into fullscreen remotely, see **Projector display**)), log out; a top bar under 820px), `OutputWindowProvider` (`outputWindow.tsx`: the output window handle from `useOutputWindow()`, `setOutputFullscreen()`, shared by the sidebar and the kick-off check), `LiveDataProvider` + `TeamsProvider` (`teamsContext.tsx`), the five pages, and the offline / save-error warnings (fixed bottom right). `useHashPage()` hides pages by hash (Live is the default); all stay mounted, so document-level key handlers must check the page is visible and that no `dialog[open]` / `[role='dialog']` popover is open (see `PresentationPanel.tsx`). Each page starts with `PageHeader` (Live: its sticky `OnAirStrip`) and lays out in `PageBody` (`ui.tsx`).

- **Live** (`src/control/live/`, `LivePage.tsx` lays it out; scenes and score only, made to fit 1366×768): sticky `OnAirStrip` (ON AIR pill at a fixed width so nothing shifts on a take, clock readout + half + running/paused, Start/Pause, End half (End match in the 2nd half), "Clock ⋯" popover with halves, ±1m/±1s, Set time, Reset clock; a `right` slot, fed by `LivePage`'s `stripRight`, for page-wide notices such as graphics changes not on air); left: output preview and `ScorePanel` (per side: crest, name, − score +, last goal, "Who scored?" popover); right (first below 1000px): `ScenePanel` (GOAL! then "In play" / "Pre-match" / "Breaks" tiles with hint lines, red frame on air; player card picker with the latest scorer first and the on-air player named), `PresentationPanel` (always shown at a fixed height, disabled until the intro is on air), `LineupRow` (counts + Edit lineup dialog). Without a home team it shows a prompt linking to Match setup.
- **Match setup** (`src/control/match/`): `MatchSetupPage.tsx` (1 · Teams with `TeamPicker` searchable comboboxes and the away players switch, 2 · Lineup, Kick-off check, Reset), `LineupEditor.tsx` (playing list in intro order with drag / ↑↓ / Bench, not playing list with Add, Pick all / Clear; give it `key={side}`; also `SideTabs`, `useLineupSide`). Changing a team asks first when its lineup is picked (it gets cleared) or the match is under way (clock run or goals).
- The Teams page in `src/control/teams/` (`TeamsPage.tsx`: toolbar (search, filter chips All / In match / No logo / No photos, sort), table with 25 rows per page, and the team drawer with Details and Squad tabs, beside the table from 1280px and over it below; `Roster.tsx`: the Squad tab's photo-card grid). List building blocks (`SearchInput`, `Chip`, `Badge`, `Pagination`, `Segmented`, `FileButton`, `readPref`/`writePref`) are in `ui.tsx`, the Graphics page in `src/control/graphics/` (`GraphicsPage.tsx`: header, status bar, Ctrl/Cmd+S, overview / editor routing; `draftContext.tsx`: `GraphicsDraftProvider` / `useGraphicsDraft()`; `LookControls.tsx`: look bar and Edit look dialog; `Scenes.tsx`: gallery and scene editor; `status.tsx`: the state dots and legend; see **Graphics page flow**).
- Shared building blocks are in `src/control/ui.tsx`: `Panel`/`PanelTitle`/`PanelBody`, `Button` with variants (takes a `ref`), `CommitInput`, `Thumb`, `UploadButton` + `useImageUpload`, `PanelBoundary`, `Popover` (anchored panel, Esc / outside click, focus return) and `Dialog` (native `<dialog>` with `showModal()`; backdrop closes only on a click that started there). Both close on `hashchange`, since hidden pages stay mounted.
- **Styling is Tailwind v4**, configured CSS-first in `src/control/index.css` (`@theme` tokens such as `bg-panel`, `text-dim`, `border-line-strong`; global form/button styles in `@layer base`). Merge classes with `cn()` (tailwind-merge), so a `className` overrides a variant. Only the control page imports Tailwind.
- **Time-derived UI** (clocks) uses `useTicking(nowMs => value)` (`src/shared/react/hooks.ts`) in the smallest component possible. It checks every 250 ms but re-renders only when the value changes.
- Text fields use `CommitInput`: saves on native `change` (blur/Enter/closing a colour picker), not per keystroke, and snapshots don't overwrite a focused field. Give it (or its form) a `key` per record so switching records resets it. `onCommit` returning `false` rejects the value and resets the field to the stored one.
- React escapes text, so user input is safe in JSX. Never use `dangerouslySetInnerHTML` with user text; the output page is public.
- **Previews** (`src/control/OutputPreview.tsx`) embed the real output page in an iframe scaled from the 2304x1024 canvas. The Graphics preview forces a scene through `postMessage({ type: "preview-scene", scene })` (or `?scene=`) and unsaved scoreboard colours through `postMessage({ type: "preview-graphics", graphics })`. Unsaved scene settings (e.g. the Graphics draft, `applyDraft(onAir, draft).scenes`) go as `postMessage({ type: "preview-scenes", scenes })`, merged per scene over the saved configs. The output page then shows them locally without going on air. The Graphics preview iframes (and gallery thumbnails) are created on first visit only, and dropped again while the Graphics page or their view is hidden (`OutputPreview`'s `active` prop; the gallery's `thumbnails`). Static thumbnails re-send `preview-data` when the static page posts `static-ready`. `OutputPreview` posts each message kind only when its content changes (`contentKey()` in `src/control/previewData.ts`: data URLs keyed by length and tail) and re-sends them on the iframe's `load`; it sends only the changed scenes (`toAirScenes`) as `preview-scenes`. All preview messages are typed in `src/shared/previewMessages.ts`.
- **Static thumbnails** (`staticOutputUrl(overlayUrl(), scene)` → `src/overlay/static.html?scene=<type>`, a third Vite page, entry `static-main.tsx`) are for galleries of small still previews. The page has no background video and never imports the store, so Firebase never loads (the on-air page stays one bundle). `StaticLiveDataProvider` (`overlay/static.tsx`) takes a full `LiveData` from `postMessage({ type: "preview-data", data })` (structured clone keeps the players Map) and renders nothing until the first one. Once its listener is registered it posts `{ type: "static-ready" }` (`STATIC_READY` / `isStaticReady` in `previewMessages.ts`) to `window.parent` with `location.origin`, and the control resends `preview-data` on it (an iframe `load` can come before React mounts the listener); it only accepts messages from `window.parent`. Only the forced scene's section renders, with a `cut` transition; `body.static` jumps every CSS animation to its end state; `useStaticMode()` lets scenes skip timers (SponsorRotation shows the first sponsor, clocks compute once via `useTicking(fn, null)`). The other preview messages work too. `StaticScenePreview` (`OutputPreview.tsx`) creates the iframe when it scrolls into view (IntersectionObserver) and posts `thumbnailData(live, shown, scene)` (`src/control/previewData.ts`, tested): the data trimmed to that scene (photo only of the intro / player card's player, other scenes' images dropped, sponsors only for the sponsors scene), posted only when its `contentKey` changes. Never post the full `LiveData` to many thumbnails.

## Output page

`src/overlay/Overlay.tsx` renders one `<section data-layer="<sceneType>">` per scene (components in `scenes.tsx`, `SCENES`), shows it through `data-tr` (see **Transitions**) and sets `body[data-scene]`. A scene's `background` image replaces the default video. The `<video>` stays static in `overlay.html`, because React doesn't render the `muted` attribute that autoplay needs. Keep the overlay's class names and markup in step with `overlay.css`, which is plain CSS (no Tailwind) on purpose. The intro is keyed by player so its entry animations replay for each player.

`overlay.css` targets a ~2.25:1 canvas (2304x1024). Everything is positioned in `%` and sized in `vw`, so the page scales to any screen or window of the same aspect ratio. Avoid fixed `px` sizes there. Non-scoreboard scenes draw on a solid `.card` so they read on any background. Team colours come in as `--team-primary` / `--team-secondary`, and the colour scheme's highlight as `--accent`. The player intro follows the design from Figma (Granicar file, node 1408:23320): team-colour band, crest, first name over a larger surname, PNG cut-out on the bottom edge. It is sized in `vh` (its design is 16:9) and long names are shrunk by `fitLines()` (`IntroName`).

**Projector display** (`src/overlay/display.ts`, top-level page only; the control previews embed the page in iframes and skip it). The output runs in a browser window on the projector / second screen for the whole match, while the operator keeps their own browser on the control page. Browsers allow fullscreen only after a click in that window, so the control's Fullscreen button sends `{ type: "output-fullscreen", on }` with `postMessage(…, { delegate: "fullscreen" })` (fullscreen capability delegation, Chrome/Edge 104+), and the output calls `requestFullscreen()` in its handler. Elsewhere, the output goes fullscreen on its first click or key press (Esc leaves). The output reports `{ type: "output-state", open, fullscreen }` to `window.opener` on load, on `fullscreenchange` and on `pagehide`; the control keeps `e.source` as its handle (`useOutputWindow()` in `App.tsx`) and, after its own reload, asks for a new report on the `OUTPUT_CHANNEL` BroadcastChannel (protocol in `src/shared/outputWindow.ts`). The pointer is hidden in fullscreen. The page holds a Screen Wake Lock so the display never sleeps, takes it back when visible again (the browser drops it when hidden) and every 30 s, and restarts the background video if the browser paused it.

**Theme and colour scheme: global, for every scene.** Both live in `src/shared/themes.ts` and are stored together in `settings/graphics` as `{ theme, colors, transition }`. Don't call them "templates" any more.
- **Theme** (`THEMES`) = the design of every scene. Three: `classic` (the original design: white clock tab, crests and big score over the video), `dark` (crest, score and name per side with the timer and half in the middle; CSS classes `sb-bar`/`bar-*`) and `semafor` (black stripes turning slowly (SVG bands, CSS rotation, `SemaforStripes`) under a panel that blurs and darkens them with `backdrop-filter`, showing names + team `city`, clock, crests with scorers by surname, the competition logo (scoreboard scene's `logo`, else its title/subtitle; edited in the Graphics "Competition" panel, shown only with this theme) and score). `ScoreboardScene` branches on the theme id; the overlay sets `body[data-theme]` so `overlay.css` can restyle any other scene per theme. Semafor does: `Overlay.tsx` draws `SemaforStripes` once behind all scenes (so they keep turning across scene changes), `.card` and the intro's default background become the same blurred panel as `.sem-panel`; transitions keep the blur working (see **Transitions**). Classic and Dark scenes still share the original look. Each theme names its default colour `scheme`.
- **Colour scheme** (`COLOR_SCHEMES`) = a named `SchemeColors` set that works with any theme: Classic, Semafor, Dark, Midnight, Forest, Ember, Gold, Steel. `background` (null = video) is behind every scene without its own image (`body.has-bg-color`); `highlight` is every scene's `--accent` (card border, titles); `score`/`names`/`timer`/`accent` colour the scoreboard as `--sb-score`, `--sb-names`, `--sb-timer`, `--sb-accent`. `THEME_COLORS` lists the colours each theme's editor shows, with labels. The scheme shown as selected is derived with `matchingScheme()` ("Custom" once a colour is edited); no scheme id is stored. `SceneConfig.accentColor` is no longer used (kept for per-scene overrides later).
- **Old data:** `normalizeGraphics` reads the pre-themes `template` field; the old ids `midnight`/`forest`/`ember`/`gold`/`steel` become Dark in that scheme (`LEGACY_THEMES`), and a missing `highlight` comes from the scheme the other colours match, else the theme's.
- **Graphics page flow** (see **Graphics draft**). Every Graphics edit (theme, colours, transition, each scene's layout, texts, background, seconds per sponsor, Competition logo) is in one of three states, colour-coded everywhere (legend in the header, dots on fields, cards, the scene strip and the sidebar item): **unsaved** (blue; `local` in `GraphicsDraftProvider`, mounted in `App.tsx` around the pages, so it survives page switches; beforeunload warns), **saved, not on air** (amber; the shared stored draft) and **on air** (red). The provider exposes `onAir`, `stored`, `changes`/`pending`/`summary`, `saved`, `shown = applyDraft(onAir, stored, local)`, `unsaved`, `toAir` and the actions: `edit(patch)` (keeps `local` minimal against `saved`), Save (`save(diffDraft(onAir, shown), stored)`; button or Ctrl/Cmd+S while the page is visible, which commits a focused field first), Put on air / Save & put on air (`publish(diffDraft(onAir, shown))`, with a confirm naming what changes), Discard (unsaved only) and Revert to on air (`discard()`, confirm). The sticky status bar shows the unsaved or saved-not-on-air summary with those buttons. Nothing on the page writes on air directly. Page layout: the overview (`#/graphics`) has the "Look · all scenes" bar (Theme, Colour scheme, Transition as popover pickers; the Transition one has a small preview that plays the pick or Replay; Edit look opens a dialog with a preview, all pickers and the single colours, Reset colours = the theme's own scheme) and a 3-column gallery of the nine scenes (static thumbnails of `shown`, layout/background meta, red On air badge for the program scene, change dot). A card opens the scene editor (`#/graphics/<scene>`; `useHashPage()` takes the first segment): ← All scenes, prev/next, the scene strip, a big preview ("Preview only · not on air", toggle Your version / On air now = null overrides) and the scene's settings (`SceneSettingsPanel`, Competition on Semafor's scoreboard) editing `local`. Picking a theme keeps the colours; picking a scheme replaces them all. Elsewhere: Live's on-air strip shows "Graphics: … not on air" (→ `#/graphics`) while `pending`, and Match setup's kick-off check has "No unsaved graphics changes". Per-scene customisation of the look comes later.
- Classic's defaults reproduce the original look exactly. To add a theme, add it to `THEMES` and `THEME_COLORS` (plus markup in `ScoreboardScene`, a `ThemeThumb` in `control/graphics/ThemePanels.tsx` and CSS); to add a colour scheme, add it to `COLOR_SCHEMES`.

**Scene layouts.** Within a theme, a scene can have several layouts: `SCENE_LAYOUTS` (same file) lists them per scene, the choice is `SceneConfig.layout` (normalized with `sceneLayoutId()`, default `"standard"`; stored as `template` before themes, which `normalizeScenes` still reads), picked in the scene's settings on the Graphics page, and the scene component branches on it. Welcome has `standard` (the card) and `largeText`: the title and subtitle in screen-high letters scrolling right to left on a loop (`Marquee` in `scenes.tsx`). Its track is two identical groups moved by 50%, each repeating the phrase to cover the screen, and its duration follows the measured width so the speed stays `MARQUEE_SPEED`. Sponsors has `grid` and `single` (see **Sponsors**).

**Transitions** (global, `GraphicsSettings.transition`, default `fade`). Every scene change on the output page plays one, including in the control previews. `src/shared/transitions.ts` lists them (`TRANSITIONS`). Kinds: `cut`; `fade` (crossfade); `popup` (old scene shrinks away, new one pops in with an overshoot); and `cover` (wipe, staggerWipe, blinds, shutter, doors, iris, pixels). A cover's curtain closes over the old scene, holds with the team logo, and opens on the new one. All of them are recreated from motion.dev's (paid) page transitions with no dependency. `transitionFrame(kind, frame)` is the pure, tested timeline. **Everything runs at 30 fps:** progress moves in whole 1/30 s frames (`frameAt`). `useSceneTransition()` (`src/overlay/Transition.tsx`) renders only at start and end. In between, a `requestAnimationFrame` loop writes the `--tr-*` variables on `body` when the frame changes, so there is no React render per frame. A timeout finishes the transition even if animation frames stop, so a curtain can't stay on air. Scenes are shown by `data-tr` (`on`, `<kind>-in`, `<kind>-out`, absent = hidden). Fades go on a scene's children, never the section, so Semafor's `backdrop-filter` keeps working (the section only gets opacity 0/1 or a transform). `TransitionCurtain` draws the cover pieces in `--c1` (scheme `highlight`) and `--c2` (scheme `background`, else dark), with the logo of the scene's team (else home); the CSS is at the end of `overlay.css`. A new take before the swap retargets the running transition; after it, the next one starts when it ends. The page background (scene image or scheme colour) and `body[data-scene]` follow the scene shown, which changes at the swap (under a curtain). The Graphics preview replays a transition with `postMessage({ type: "preview-transition" })`. To add one, add it to `TRANSITIONS`; a cover also needs a case in `CurtainPieces` and CSS.

Big Shoulders is loaded as a variable font with an optical-size axis. `body` pins `"opsz" 14`, which reproduces the static cut the scoreboard was designed with; the intro uses `"opsz" 72` (first name) and `26` (surname) at weight 400 to match its design. Check scoreboard glyph sizes if you change the font link. The background is `public/media/SemaforBG.mp4`, played at 0.5x (rate is re-applied on `loadedmetadata`). The page uses the Big Shoulders font and does **not** load the control page's Tailwind theme.

## Workflow

Work is tracked on the Trello board **Scoreboard**: https://trello.com/b/9oE94fk7/scoreboard (managed by the `boarder` agent, see `.claude/agents/boarder.md`). Four lists following the branch flow:

| List | Card is here when | List id |
|---|---|---|
| TODO | Captured, waiting to start | `6adf32815972ae2e28f6f451` |
| In progress | Feature branch, PR into `staging`, reviews and tests | `6adf3282ff1ede364a933e6d` |
| Staging | Merged into `staging`, being verified on the preview | `6adf32835331b84891be432c` |
| Prod | Merged into `main` and deployed | `6adf328337bdc49c573a7ef3` |

A card that fails verification on Staging goes back to In progress with a comment.

**Every change gets a card.** Before changing code, config, rules or docs in this repo (feature, bug fix, design, refactor, chore), have `boarder` create a Trello card with a full description, or reuse the card the work already has, and move it to In progress. No change without a card, however small. When the work is done, have `boarder` comment what changed (files, branch/commits, test and build results). Mention the card link in your reply, and in the PR description when there is one. Questions and read-only analysis don't need a card.

**`product`** (`.claude/agents/product.md`) is the Senior Product Manager: feature ideas, priorities, shaping vague requests into specs, branding, customer segments and handling. It never changes code; ideas the user accepts become TODO cards via `boarder`.

**`/feature <request>`** (`.claude/skills/feature/SKILL.md`) runs a change through the whole agent flow: spec for features and designs (`product`) → card (`boarder`) → design when it crosses layers (`architect`) → implementation by the owner (`control-ux-reviewer`, `design-maker`, `architect`) → reviews (`offline-reviewer`, `overlay-reviewer`) and `tester` → fixes (max 2 rounds) → `npm test` + `npm run build` → card comment → report. It never commits or pushes on its own.

## Conventions and gotchas

- Import shared code via the `@shared/*` alias (configured in both `vite.config.ts` and `tsconfig.json`).
- TS is `strict` with `noUnusedLocals`/`noUnusedParameters`. `npm run build` fails on unused code.
- Fire-and-forget store writes from UI handlers use `void promise`.
- `@vitejs/plugin-react` is pinned to v5 because v6 needs Vite 8, and vitest 2 is on Vite 6.
- Vite `base` is `/obs-scoreboard/` (overridable with `VITE_BASE_PATH`; staging uses `/`). Built pages keep their `src/...` paths: `/obs-scoreboard/src/overlay/overlay.html`.
- The Firebase config in `.env.*` is a public client identifier, not a secret. The staging service-account key is a secret and lives only in the GitHub secret `FIREBASE_SERVICE_ACCOUNT_STAGING`.
- `src/SemaforBG.mp4` looks like an unused duplicate. The overlay references `public/media/SemaforBG.mp4`.
